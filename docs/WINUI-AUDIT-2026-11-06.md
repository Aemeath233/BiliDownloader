# WinUI 3 自动化测试与代码审查

2026 年 11 月 6 日。本轮审查覆盖 C# 解析与下载核心、WinUI 3 页面、持久化、凭证保护和自动化脚本。

## 验证结果

Release 配置下，23 项核心测试、26 组 UI 检查和发布版启动退出检查通过。UI 检查包含 7 组基础回归和 19 个完整交互场景。本机显示缩放为 150%，使用独立测试账号文件、独立下载目录、模拟 HTTP 接口和本地生成的真实媒体。

- 1,000 条历史记录，200 集合集，4 个同时进行的模拟下载。
- 80 次连续切页，以及搜索、过滤、跨过滤选择、批量选择、取消和重复任务提醒。
- 760×560、980×640、1080×720 三种逻辑窗口尺寸，分别检查浅色和深色主题。
- 键盘焦点遍历、Ctrl+L 定义、原生可访问名称与 Invoke 模式、主操作按钮命中区域。
- 真实 H.264/AAC 文件下载与封装，三种模式的输出音轨检查和编码包 SHA256 比对。
- 旧式音画合流提取、备用地址、截断流、品质不符、取消后重试、并发同名发布和退出恢复。
- 登录文件只读时的错误处理、DPAPI 迁移、迁移备份、重定向边界和日志脱敏。
- 全新目录执行生产配置 publish，检查应用资源，启动独立用户目录，等待窗口和运行时就绪，再发送正常关闭请求并要求退出码为 0。

本轮本地结果位于 `build/native-verification/2026-11-06-accepted/`，包括 `summary.json`、`core/report.json`、`ui/experience-report.json`、`ui/experience-trace.jsonl`、`publish/report.json` 和 36 张 UI 截图。原始运行输出由 Git 忽略，仓库保存本报告与可复跑的脚本。复跑方法见文末。

## 已修复的审查发现

| 优先级 | 触发情形与影响 | 修复与验证 |
| --- | --- | --- |
| P2 | 登录刷新 POST 收到跨源 307/308 时，表单中的 refresh token 可能被发送到跳转站点 | 请求层拒绝携带表单的跨源跳转。恶意跳转夹具验证秘密表单不会到达目标站点 |
| P2 | 账号 HTTPS 请求可以跟随 HTTP 跳转，Cookie 存在明文传输风险 | 请求和跳转都要求 HTTPS，分享输入中的 HTTP 地址先规范为 HTTPS |
| P1 | 重选任务品质时，原 cid 已下架会被替换成合集第一集 | 找不到原分集时显示错误并禁用下载，加入独立回归 |
| P2 | 接口 JSON 缺少 code，或 code 为小数、超出整数范围时，被默认解释为成功 | 成功判定要求有效的 64 位整数状态码，只有 0 表示成功。缺失、null、字符串、小数、超大值均加入回归 |
| P2 | 某条历史记录的 task_id 为 null 时，正则校验抛异常并中断全部历史载入 | 先拒绝空 id，再检查格式。验证坏记录后的正常记录仍可读取 |
| P2 | 旧版明文登录文件及既有备份可能继续保留凭证明文 | 读取旧格式时立即转换为当前用户 DPAPI，备份也复用相同迁移逻辑 |
| P2 | 登录文件不可删除时，退出登录事件中的文件异常可能使窗口崩溃 | 捕获错误并显示提示，失败后保持有效会话。只读文件场景通过 |
| P2 | 日志页每 500 ms 更换数据源，影响滚动和阅读 | 日志内容没有变化时复用数据源，验证列表引用与滚动位置稳定 |
| P2 | 千条队列逐项筛选产生大量集合通知与控件创建 | 批量更新可见集合，进度刷新复用行，按状态延迟创建操作按钮，减少视口外缓存 |
| P2 | 主下载按钮使用图标与文本组合内容，辅助工具获取不到清楚的名称 | 增加明确的可访问名称，并验证键盘和原生 AutomationPeer |
| P2 | 小字号状态文本在深色主题下对比不足 | 按主题选择状态颜色，检查小字号文字对比度至少 4.5∶1，复选框描边与勾选至少 3∶1 |
| P2 | 底栏把排队任务也显示为进行中，容易误解并发限制 | 分别显示正在进行与排队数量，验证 4 个进行中、1 个排队 |
| P2 | 测试复用旧报告时可能产生误判 | 使用独立报告与全新测试程序目录，同时检查新报告、进程退出码和每项结果 |
| P1 | 普通 build 可以启动，但生产 publish 漏掉应用自身的 PRI 与编译 XAML，发布版启动崩溃 | 项目显式把应用资源加入发布清单，缺少 PRI 时直接令发布失败。新增独立生产发布检查，实际启动和正常退出通过 |
| P3 | 历史记录逐条遍历检查重复 id，载入成本呈平方增长 | 使用 HashSet 去重 |
| P3 | 任务结束后速度采样字典继续持有条目 | 任务清理阶段移除速度采样 |
| P3 | 长前导点文件名截断后可能变为空字符串 | 截断后再次检查并回退为 untitled |

主要修复位置包括 `src/BiliDownloader.Core` 下的 `Network.cs`、`AuthService.cs`、`AppRuntime.cs`、`DownloadManager.cs`，以及 `src/BiliDownloader.WinUI` 下的 `MainWindow.xaml.cs` 和 `Rows.cs`。

安全重定向使用受控的恶意响应夹具验证，线上接口是否存在可利用的外部跳转入口需要另行确认。

重选品质的模式与本次目录也加入回归。程序化填入源链接时会识别对应的文本变更事件，避免再启动一次普通解析覆盖任务上下文。

状态码与空 id 的新用例在修复前稳定复现两项失败，修复后全部通过。修复前本地报告位于 `build/native-verification/2026-11-06-edge-before/report.json`。

## 响应耗时

以下取最终一次完整运行。切页数字从发起导航开始，测到低优先级调度回调及布局更新完成。搜索数字包含过滤与可见集合更新。滚动数字包含大跨度跳转后的布局与容器回收。

| 项目 | 本机结果 |
| --- | --- |
| 进程启动到 UI 初始化就绪 | 约 817 ms |
| 80 次切页中位数 | 3.90 ms |
| 切页 P95 | 40.37 ms |
| 切页最大值 | 91.06 ms |
| 千条队列搜索最大值 | 56.59 ms |
| 12 次大跨度滚动平均值 | 约 81 ms |
| 大跨度滚动最大值 | 约 132 ms |
| 生产发布版窗口与运行时就绪 | 约 622 ms |

第一轮同类千条队列搜索曾出现约 436 ms 的峰值，随后多轮复测最大搜索耗时约 49–79 ms。数据会受系统负载、缓存、渲染和垃圾回收影响，单次测量适合定位卡顿与比较本机改动。

常规操作的响应已经缩短，大跨度跳转滚动仍有可观察的布局成本。这里测量的是调度和布局，GPU 呈现帧率、鼠标滚轮逐帧表现与显示器上的最终动画还需要专门的帧级采集。

## 视觉与操作审查

以下是对脚本截图和实际控件状态的审查判断，审美与理解成本包含主观判断。

- 页面使用统一的正文和标题层级，合集分集保持单行，完整标题可通过悬停查看。底部的本次目录和主下载按钮持续可见。
- 单视频省去分集选择。宽窗口把下载内容与品质并排，窄窗口纵向排列，减少跨越整窗的长表单感。
- 进行中任务提供取消，完成任务提供打开、定位和移除，失败任务提供重试与品质重选。按状态呈现操作能减少同时出现的按钮。
- 顶部四个文字入口便于识别。脚本检查了在最小测试窗口下导航、品质选择和主要下载操作的可达性。
- 设置直接显示同时下载数量与限速，开关采用横向排列。底栏把排队与正在进行的任务分开描述。
- 同一组操作在深浅主题中使用一致的标签、位置和选中反馈，状态文字保留明确的中文含义。

当前页面已经能清楚完成解析、选择内容、下载和打开文件的主流程。长队列仍需要继续压缩大跨度滚动时的布局成本。失败任务的“重新选择品质”目前放在省略号菜单里，首次使用时的可发现性仍有改善空间。脚本可以验证入口、状态和布局，人对界面是否自然、是否喜欢的判断仍需实际使用反馈。

本轮使用小视口外缓存与 x:Load 延迟创建次要控件，依据 WinUI 的列表与 XAML 加载机制进行调整。[微软列表性能说明](https://learn.microsoft.com/en-us/windows/apps/develop/performance/optimize-gridview-and-listview)、[微软 x:Load 说明](https://learn.microsoft.com/en-us/windows/apps/develop/platform/xaml/x-load-attribute)。

## 分发依赖

Windows App SDK 改为按 WinUI 组件引用。包含应用 PRI 与 XBF 后，Release 自包含目录从约 219.4 MiB 降到约 168.9 MiB，减少约 50.6 MiB。该数字是展开的程序目录体积，安装包应在最终打包后另行测量。

发布资源遗漏与 Windows App SDK 已记录的非打包发布问题一致。本项目增加发布资源清单，并用实际生产 EXE 检查资源是否足以启动。[Windows App SDK 问题记录](https://github.com/microsoft/WindowsAppSDK/issues/6720)。

NuGet 已知漏洞扫描没有报告公开漏洞，本地原始结果位于 `build/native-verification/2026-11-06-accepted/dependency-audit.json`。扫描范围为当前项目及传递 NuGet 依赖。

## 复跑方式

在项目根目录的 PowerShell 中运行。

```powershell
.\scripts\verify_native.ps1
```

该入口运行核心测试、完整 UI 场景、生产发布启动退出检查和 NuGet 扫描。需要 .NET 10 SDK、Windows SDK，以及已有的开发用 FFmpeg、ffprobe 和精简 FFmpeg。程序安装后的用户环境与开发测试环境分别验证。

只检查 UI 时运行。

```powershell
.\scripts\verify_winui.ps1 -Experience
```

只检查生产发布时运行。

```powershell
.\scripts\verify_publish.ps1
```

报告默认生成到 build 下独立目录。脚本保留逐步追踪、结构化结果和 PNG 截图，通过后清理临时 UI 测试程序，失败时保留程序供定位。生产发布目录保留以便人工复核。本轮将已验证发布目录的文件复制到 dist/winui-reviewed，并逐个校验 SHA256 与文件清单。

## 验证边界

- HTTP 请求由测试处理器模拟，真实 B 站扫码、会员权限、地域限制、风控和服务端接口变更需要实网验收。
- 封装测试使用真实的本地媒体与 FFmpeg，HTTP 侧的音视频传输使用夹具。
- 本机实际测试的显示缩放为 150%，其他 DPI、显示器切换、系统高对比度和屏幕阅读器整套工作流需要进一步验收。
- 截图来自原生 XAML 渲染树，适合检查布局与状态。视觉审查没有替代 GPU 帧率测试和真实用户可用性测试。
- 干净系统上的安装、升级、卸载和依赖交付需要在最终安装包形成后验证。
