# 界面与流畅度审查（2026-10-29）

本次范围：`bili_client/ui`、运行依赖、打包资源与界面回归。项目使用 CustomTkinter/Tk，不是浏览器前端；frontend-code-review 中的 React/Dify 专用规则不适用。

## 结论

当前下载服务没有必须推倒重做的证据。后台 I/O、共享动画调度器、页面复用、队列分页和字段差异更新都已经存在。主要问题是展示层的切换方式、无效动画工作及偏向管理后台的视觉层级。包体积、启动速度、交互流畅度需要分别处理。

## 已处理

| 问题 | 触发与影响 | 修正 |
| --- | --- | --- |
| P2：隐藏按钮仍注册颜色动画 | 创建队列、更新未显示控件时，状态配置也进入逐帧调度，和控件创建争用事件循环 | 隐藏按钮、颜色相同的按钮直接更新最终颜色；可见按钮保留颜色反馈，并在首次配置前保存旧颜色 |
| 首次切页插入整屏加载提示 | 本地构建页面前先遮住旧内容，加载提示短暂出现，随后页面再移动 | 保留旧页直至新页构建完成，直接呈现新页；请求标记仍拦截过期切页 |
| 整页位移动画与原生子控件创建同时发生 | 页面用 `place` 移动 180ms，进入队列时卡片还在分批创建；存在重复暴露、移动子窗口的开销路径 | 取消整页位移，保留导航指示条、按钮、进度与提示反馈。未测量实际帧率，不据此承诺达到特定 FPS |
| 信息层级偏重 | 顶栏三块统计和队列四块统计占据较多垂直空间，进行中/排队信息重复 | 顶栏去掉卡片底色，队列统计改为紧凑单行，收窄侧栏最小宽度 |

视觉方案沿用现有语义：白色面板 `#ffffff`、浅蓝灰背景 `#f3f6fb`、正文 `#0f172a`、辅助文字 `#64748b`、主要操作粉 `#fb7299`、信息蓝 `#00a1d6`，深色使用现有双主题颜色。字体保留 Microsoft YaHei UI，标题 22px、内容标题 20px、正文 12–14px。左对齐，减少统计卡片层级，把更多高度留给链接和任务。没有引入新的配色、字体依赖或装饰动画。

## 测量与限制

- 最终验证：127 项 unittest 回归全部通过；Ruff 代码检查与格式检查通过。新增覆盖首次切页保留旧内容、隐藏按钮不注册动画、可见按钮变色和同色更新。
- Windows / Python 3.11，在隔离的 Mock 服务窗口首次创建设置页约 225ms、队列框架约 92ms、日志页约 77ms。单次观察，受系统负载影响；不是下载测速，也不是改动前后帧率对比。
- 同样的 30 条任务、窗口隐藏、动画开启，仅替换按钮过渡实现进行对比：旧实现注册 186 次隐藏按钮 tween，新实现 0 次，两次均创建 30 张卡片。这只量化无效动画注册，不代表整体速度提高相同比例。
- 本地便携 EXE 108,929,273 字节（约 103.88 MiB）。FFmpeg 的 avcodec/avfilter DLL 合计 192,335,360 字节（约 183.43 MiB，未压缩），说明媒体依赖是包体积的重要来源。未进行打包内容裁剪。
- 现有 `.venv` 指向已不存在的 Conda Python，本次使用 `uv run --no-project --python 3.11 --with-requirements requirements-dev.txt` 验证，未修改原虚拟环境。
- Windows 截图工具两次捕获超时。本次参考仓库既有截图，执行实际 Tk 回归；修改后的像素布局与动态观感仍需人工验收。没有访问真实账号或发起下载，也没有重新打包 EXE。

## 尚存成本与建议

设置页首次访问仍会同步创建 132 个 Tk 控件，队列一页最多创建 30 张复杂卡片。这些成本没有被本次切换方式调整消除。如果后续继续使用 Tk，优先把高级设置按需展开、减少每条任务常驻按钮、再依据实际长队列滚动测量决定是否只创建可见行。

主流程宜保持“粘贴链接 → 选择必要选项 → 下载”，设置和日志作为次要入口。后续视觉重构应优先合并重复统计、隐藏不可执行的任务操作，并让未解析时的选择区域更简洁，而不是继续增加动画。

如果产品目标明确要求网页级的样式、滚动与过渡控制，建议保留 Python 服务，将展示层替换为本地 HTML/CSS + pywebview/WebView2。现有服务与 Tk 页面分层提供了复用基础；仍需重新实现命令桥接、状态订阅和界面，并验证 WebView2 Runtime 分发、打包及实际内存成本，不能把换框架当作自动变快或变小的保证。本轮不进行框架迁移。
